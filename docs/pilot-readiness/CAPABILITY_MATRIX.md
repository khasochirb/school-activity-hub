# Current Capability Matrix

## Audit method

This inventory reflects repository evidence as of 2026-07-17. A route, navigation item, table, type, or unfinished interface was not treated as an end-to-end capability by itself. "Implemented and verified" is reserved for facts that can be established directly from static configuration or dependency inspection; runtime workflows generally remain "needs testing" because the repository has no automated test suite and this audit did not use real student data.

Status vocabulary:

- **Implemented and verified**: static evidence is complete for the stated claim.
- **Implemented but needs testing**: the workflow and protections are connected in code but lack sufficient automated/live verification.
- **Partially implemented**: useful elements exist, but the complete pilot workflow or governance control does not.
- **Not implemented**: no usable end-to-end capability was found.
- **Cannot determine from repository**: depends on live infrastructure or external practice not represented here.
- **Requires school/policy decision**: implementation depends on an unresolved operational, legal, ethics, or school choice.
- **Explicitly deferred**: the repository or approved scope expressly excludes it.

## End-to-end evidence notes

### Authorization and identity

- Student join logic hashes the submitted one-time code, validates active/unused/unexpired status and an active roster record, creates the Supabase user server-side, creates the student profile, links the roster, and conditionally redeems the code. This is materially stronger than open signup, but concurrency and failure cleanup still need automated testing.
- School and platform authorization use different models. Platform administration is not a value in the school `profile_role` enum and does not automatically make a platform administrator school staff.
- The service-role client is server-only in repository structure. Its safe use still depends on every call retaining a preceding authorization and input-validation check.

### Event and attendance integrity

- Staff-created events can be approved directly; club-leader events enter pending approval. Approved shared events use explicit `event_school_shares` rows and approved school connections.
- Registration performs capacity checks in application code. Without a transactional database constraint/function, simultaneous final-seat requests remain a scenario to test.
- QR check-in verifies identity, active school/roster relationship, event approval, registration, sharing eligibility, and duplicate state. The QR URL is a convenience path, not an authorization secret.
- The database can represent manual/admin check-in methods, but that representation is not a usable fallback workflow.

### Privacy, safeguarding, and evaluation

- Permission tracking records only a status; it is not parent information, consent evidence, or a parent workflow.
- Risk labels are not a safeguarding response system. No confidential reporting, restricted case management, local referral, or emergency response workflow is present.
- Platform audit logs cover platform administration, not routine school administration. Audit expansion must be deliberately minimized rather than logging complete student records.
- Current dashboard and report counts are operational analytics. They are not an approved research dataset or evaluation protocol.

### Operations

- Region configuration is present, but repository inspection cannot prove production uptime, live environment settings, provider backups, restoration success, or support readiness.
- Fake seed records in the canonical schema are acceptable only for a separated non-production environment. Their presence creates a launch gate until the production migration/seed process is documented and verified.
